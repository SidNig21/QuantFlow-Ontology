# 04 — Agent Observability & Optimization

The product-launch talk for **AIP Evolve**, staged on top of Agent Manager's telemetry layer. Two speakers: one walks a live manufacturing demo (delivery-fulfillment agent, urgent rear-bench-seat work order) to show what "production ready" telemetry looks like; the second launches Evolve, an agentic optimizer that consumes that telemetry and rewrites the agent to hit a stated objective (in the demo: latency).

## The argument, compressed

1. Having durable execution + Agent Engine primitives isn't "production ready." Production ready means answering three questions per agent: **is it correct** (right outcome), **is it performant** (fast, efficient, not over-using compute), and **is the workflow debuggable** (can a human trace how a multiplayer process — agents + humans — reached a terminal state, and attribute delay to the right upstream step, e.g. a late delivery traced back to procurement, or patient discharge traced back to intake).
2. Palantir's answer to "debuggable" is layered telemetry with **no extra logging work from the developer** — every agent emits it for free because it runs on the ontology: raw traces/logs (OpenTelemetry-compatible) → a **structured narrative** (LLM calls, actions, object writes) → multiple *lenses* on the same underlying event (AIP Logic transform view, the durable-compute ledger, and **AIP Inspect** for the non-technical operational user who just needs the reasoning, not the plumbing).
3. **Agent Timeline** zooms out from a single trace to the ontology object's full lifecycle. Killer detail from the demo: 83% of "agent time" on the work order was actually a human not responding to a request-for-quote chatbot — the fix wasn't optimizing token usage inside the LLM calls, it was replacing the chatbot with a form. Observability's value is in exposing *where* the time actually goes, which is often not inside the agent at all.
4. **AIP Evolve** (the launch): point it at an agent, set a North Star objective (cost, latency, or eval score), configure a validation strategy (existing evals or auto-generated ones from production data, metric-based or LLM-as-judge, tunable output-divergence tolerance), set the allowed action space (model swap, prompt rewrite, tool/harness changes, even architectural changes — deterministic logic vs. agent-backed), and an iteration budget. Evolve then hands the job to **AIP FDE**, which fans it out into parallel subagents that each try a change, run it against the evals, and get pruned or kept — visualized as an **agent lineage graph** (one node per iteration/experiment).
5. Demo result: the delivery-fulfillment agent went from 32s (three-quote case: 45s) down to 8.8s — an 81% latency cut — via a model swap (GPT-5.5 → 5.4-mini) + prompt rewrite tuned to the smaller model's quirks, plus architectural changes: replacing one dynamic ontology-query tool call with prefetched deterministic logic in-line, and removing duplicate AI-based reasoning steps. The final proposal view shows exactly what changed, why, and the eval/side-by-side diff evidence for each change — not just a metric delta.
6. Longitudinal framing: a single trace is one execution; Agent Timeline is one object's lifecycle; running long enough across many objects builds the "rich substrate" that Evolve mines. Observability and optimization are explicitly the same infrastructure viewed at different time horizons — no separate telemetry pipeline needed for Evolve to work.

## Key quotes

> "There's no homework for you, this telemetry is generated by every agent."

> "83% of the time was waiting for me to respond to a quote... an optimization here may not be just trying to take token usage out of individual agent executions... it may be as simple as replacing this chat bot with a form."

> "It doesn't matter if it just works today, it has to work tomorrow. It also has to work the next day... That's what production means. But also, ideally, it's getting better over time."

> "It can take any of your AI systems, and it will deploy teams of agents against those to optimize any objective that you have... whether you are trying to bring down token costs, whether you're trying to make something faster... or improving quality just measured by your evals."

## QuantFlow mapping

| Palantir concept | QuantFlow equivalent | Status |
| --- | --- | --- |
| Raw traces/logs (OTel) | Append-only receipts | have the proof primitive, not the OTel export |
| Structured narrative (LLM calls, actions, object writes) | Trace-tree plan (traceId/spanId over workspace/tile/session/run/turn) | specced, unbuilt |
| Multiple lenses (Logic transform / durable-compute ledger / AIP Inspect) | Single canvas view only — no separate "operator narrative" lens yet | gap |
| Agent Timeline (object lifecycle, time-in-state attribution) | Nothing — receipts are per-run, no cross-run rollup on a tile/workspace | gap |
| AIP Evolve (goal + evals + action space → agentic optimization) | Nothing — "Evolve" already flagged as QuantFlow's biggest gap | **gap, confirmed** |

Two things worth stealing directly, independent of the availability question: (1) the **time-attribution habit** — before optimizing a run, ask where time/tokens actually went, since it's often a human-in-the-loop wait, not agent compute (directly portable to QuantFlow's session/run receipts even without Evolve); (2) the **lineage-graph-of-experiments** UI pattern for showing an optimizer's search process, not just its output — relevant if QuantFlow ever builds a backtest-eval-driven agent-improvement loop (e.g., "swap strategy-generation prompt, re-run backtest suite, keep if Sharpe/drawdown eval improves without behavior divergence" — same shape as Evolve's cost/latency/eval-score North Star, just with backtest evals as the validation gate instead of LLM-as-judge).
