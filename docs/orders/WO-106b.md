# WO-106b — Close the `publish_artifact` file-read surface

status: open, cuttable — pre-build read run 2026-07-26 (`grok-4.5-high`), **eight findings, three
High, all fixed in this text**; record appended at the bottom
assignee: builder
depends: WO-105, WO-106 — both done, merged
closes: ROADMAP debt #25 (trigger FIRED)

## Objective

An agent that can call `qf_publish_artifact` can currently name **any file on the machine** and have
its contents read and stored permanently in the Kernel. Close that, without changing what the
desktop app or the founder can do.

## In plain terms

`publish_artifact` takes a file path and reads whatever is there. That is correct and necessary for
the app — it writes a report to disk, then publishes it. But WO-105 made this one of 24 tools served
to AI agents, and nothing checks *which* path an agent asks for. Measured with a canary file: an
absolute path outside anything the app uses was **accepted, read, hashed, and stored**.

After this order, an agent can only publish files it staged in a designated folder. **The app is
unchanged. The founder's file-picker is unchanged.**

**If it goes wrong:** either the founder's "publish a file" button breaks (it opens a native dialog
and passes an arbitrary path, by design), or the app's own two publish paths break, or the check
lands somewhere an agent can route around.

## RULING — where the constraint lives (architect, final)

**Ruled: the constraint is enforced at the MCP action-serving boundary, not inside the Kernel.**

The original D6 said the rejection must be the Kernel's "so it applies to every caller." **That was
wrong, and it is why this order exists separately.** Measured — there are four caller classes, and
three of them are legitimate:

| Caller | Path source | Legitimate? |
|---|---|---|
| `collab-electron/src/main/agent-host.ts:639` | `$HOME/.collaborator/agent-artifacts/<session>.md`, written moments before | yes |
| `collab-electron/src/main/a2a-bus.ts:68` | `join(COLLAB_DIR, "a2a")`, written moments before | yes |
| `collab-electron/src/windows/shell/src/renderer.js:962` | **native `openFileDialog()` — a human picks any file** | yes |
| **any MCP client** | any string it invents | **no — this is the hole** |

A Kernel-wide path restriction breaks row 3: the founder choosing a file from anywhere on disk is the
feature. So the boundary is not "the Kernel" — it is **"the untrusted caller."**

**Untrusted callers arrive through two doors, not one** (corrected at the pre-build read; the first
draft of this ruling said one, and that error would have produced a green gate over an open hole):
`registerActionTools` in `register.ts` handles *invocation*, and `installToolsListHandler` in
`discovery.ts` handles *discovery* — the latter builds its answer from `servedToolsForSchema(schema)`
and never consults the registry. **Fail-closed must bind both.** See D2.

**This matches how Palantir's own Ontology MCP scopes access — it is not an ad-hoc invention.**
Their OMCP uses a two-layer model: every call inherits the caller's own permissions, *and* a
separate, stricter restriction blocks a whole category from ever crossing the MCP boundary to a
lower-trust AI client "even if the user has access" (`vault: DevCon6/08 - Ontology MCP.md`, flagged
there as a "gap worth stealing" for exactly the "sandbox agent vs local session" trust boundary).
WO-106b is the same shape: the serving boundary applies a restriction to the untrusted MCP caller
that does **not** apply to the in-process app or the founder's dialog. The constraint living at the
serving boundary rather than in the Kernel is the *point*, not a compromise.

**Why this is not weaker than a Kernel check.** The threat is *an agent naming a path.* Agents reach
the Kernel only through the served plane. In-process callers are the app itself and the founder's own
dialog, both already inside the trust boundary. A second rogue server iterating `schema.actions` could
bypass this — that is the same residual already logged as **debt #22 (caller identity)**, unchanged by
this order and not its job.

**Fail closed.** A server that serves action tools without an artifact root configured must **refuse
to serve `publish_artifact` at all**, rather than serving it unconstrained. A missing configuration
must never silently mean "allow everything."

**`bytes` is out of scope and unchanged.** The original D6 claimed the app relies on `bytes`; measured,
it does not — the only `bytes` producers are `tools/qf-peer-bus/src/bus.ts:116-125` and
`packages/qf-kernel/src/kernel.test.ts` (11 invocations). `bytes` also cannot cross JSON, as the schema's own field
description states, so it is not an agent-reachable route. Leave it alone.

## Deliverables

**D1 — an artifact root, declared and required.** The server reads **`QF_ARTIFACT_ROOT`** once at
startup, alongside `QF_KERNEL_DB`. **That is the name — it is spelled here because the previous
attempt at this fix died of a "declared staging root" that had no spelling anywhere.**

"Absent" means **unset, empty, or whitespace-only** — all three fail closed. A root that does not
exist on disk is also absent (do not create it; a typo must not silently become a new allowed
directory). The root is resolved through symlinks **once at startup** and the resolved value is what
D2 compares against.

When the root is absent, `publish_artifact` is **neither registered nor advertised** (see D2's
two-door rule), the served action count is 23, and the server logs why.

**D1 carries a collision the author found before cutting this order — handle it explicitly.**
`expectedServedToolNames` (`tools/qf-read-tools/src/harness.ts:50-58`) derives the expected served
set from `schema.actions` filtered on `operatorOnly !== true` alone. **It knows nothing about an
artifact root.** So a naive D1 makes the served set 92 while two shipped gates — `tool-plane` and
`tool-discovery` — still expect 93, and both go red.

The resolution is **not** to weaken those gates. Every existing gate and harness that starts this
server — **`tool-plane`, `tool-discovery`, and `action-transport`** (which also boots `server.ts`
via `makeClient()` with only `QF_KERNEL_DB` today) — **configures `QF_ARTIFACT_ROOT`**, so the served
surface they assert stays 24 action tools and 93 total. The unconfigured case is exercised **only** by G3, which starts its own server instance
deliberately without a root. Two configurations, two assertions, neither weakened. If you find
yourself editing `expectedServedToolNames` to make a gate pass, stop — that is the
one-source-two-sides shape this repo has now paid for four times.

**D2 — the check, and the two doors.**

**Two doors, not one — the RULING's "exactly one door" is corrected here by the pre-build read.**
Untrusted *writes* enter through `registerActionTools` (`register.ts`), but untrusted *discovery*
enters through `installToolsListHandler` (`discovery.ts`), which builds `tools/list` from
`servedToolsForSchema(schema)` — **a completely independent code path that never consults the
registry.** Fail-closed must bind **both**: with no root, the tool is absent from the list *and*
absent from the registry. Filtering only the list leaves a live callable handler and an open hole.

**The path check.** Before `execute()` is called for `publish_artifact`, a supplied `path` is resolved
to a real absolute path and rejected unless it is inside the resolved root. Specified precisely,
because two builders disagreed on all four of these in the read:

- **Compare boundary-safely.** Use `path.relative(root, resolved)` and reject if the result starts
  with `..` or is absolute — or an equivalent that requires a separator boundary. **A bare
  `startsWith(root)` is a defect**, measured: `"/tmp/artifacts-evil/x".startsWith("/tmp/artifacts")`
  is `true`, so a sibling directory escapes. Bait (e) exists to kill exactly this.
- **Resolve symlinks on both sides** — the root once at startup, the candidate path per call.
- **A path that does not exist is rejected**, not passed through. `realpath` on a missing file throws
  `ENOENT`; that is a rejection, not an error to swallow.
- Rejection returns a Kernel-style error over the transport and **writes no row and no event**.

**D3 — nothing else moves.** `packages/qf-kernel` is untouched. `resolveBytes` is untouched. The app's
two callsites, the founder's picker, `qf-peer-bus`, and the Kernel tests all keep working unchanged.
The served tool's advertised schema still lists `path` (WO-106's `tool-discovery` gate will redden if
the advertisement drifts).

## Acceptance gates

Every gate ships with a **bait transcript**: break it, show red, restore, show green. Falsify by
editing shipping code, not a fixture switch — the standard WO-106 set.

**G1 — the hole is closed.** Through the **served** `qf_publish_artifact` tool, a path outside the
root is rejected, with **zero new rows and zero new events** (count both before and after).
*Baits, all five required:* (a) an absolute path outside the root — use a canary file, **never a real
secret** — rejected; (b) a `..` traversal normalising outside the root — rejected; (c) a **symlink
inside the root pointing outside it** — rejected; this kills an *unresolved* prefix test; (d) remove
the check and confirm (a) goes green, proving the gate is what stops it; **(e) a prefix-sibling
directory** — with root `<R>`, a real file at `<R>-evil/x` — rejected. Bait (e) was added at the
pre-build read: (c) alone does **not** kill a resolve-then-`startsWith` implementation, because
`"/tmp/artifacts-evil/x".startsWith("/tmp/artifacts")` is `true`. (c) and (e) together force a
separator-safe compare.

**G2 — legitimate publishing still works.** A path *inside* the root publishes successfully through
the served tool, and the resulting artifact's `content_hash` matches the file's bytes.

**G3 — fail closed, proven on the attack surface and not only on the menu.** In a server instance
started **deliberately without** `QF_ARTIFACT_ROOT`, all three must hold:

1. `qf_publish_artifact` is **absent from `tools/list`**, and the served action count is 23, not 24;
2. **`callTool("qf_publish_artifact", { path: <canary> })` fails** — the tool is not merely hidden,
   it is not callable;
3. after that call, **zero new rows and zero new events**, and the canary file's content hash appears
   in no artifact.

**Assertion 2 is the point of this gate, and it was added at the pre-build read.** `tools/list` is
served by `installToolsListHandler` (`discovery.ts`) from `servedToolsForSchema(schema)`, an
independent path that never consults the registry built by `registerActionTools` (`register.ts`).
Without assertion 2, an implementation that filters the *list* while leaving the *handler* registered
passes this gate green with the hole fully open — the gate would prove the menu, not the kitchen.

*Baits:* (a) make the missing root default to `/` or allow-all → red; (b) with a root configured the
same server serves 24 — proving the gate distinguishes two configurations rather than asserting a
constant; **(c) filter the tool from the list handler only, leaving `registerTool` in place** → the
list assertion still passes and **assertion 2 must go red**. If (c) does not redden, this gate is
decoration.

**G4 — the trusted callers are untouched.** `agent-path` still passes — it publishes via `path`
in-process at `run.ts:197-202`, staging into `<gate pkg>/.tmp`, which is **outside any artifact
root**, so it proves the constraint did not leak into the Kernel. `packages/qf-kernel` has no diff in
this rung. *(An earlier draft also cited `dock-registry` here; measured, it never calls
`publish_artifact` at all — corrected at the pre-build read.)*

**G5 — full cold suite.** `bun qa/run.ts --all` in a worktree with **zero `node_modules`**, unpiped,
`$?` on its own line, **with no other agent running on the machine**. `golden/` regenerates with no
further diff. Pre-install before any before/after measurement (`agent-path`, debt #23).
