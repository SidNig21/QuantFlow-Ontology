## Objective

Every write becomes one dumb tool between two machine checks — **the agent proposes; the ontology
permits** — and the one verb that records "the operator really placed this bet" is structurally
excluded from everything an agent can see.

## In plain terms

After this order, an AI seat can *do* things through the same catalogue it reads from — create a
hypothesis, start a run, publish an artifact — and every such request is checked twice by machine:
once that the request is well-formed, once that the change is legal. **The one thing no AI seat
gets is the button that records a settled real-world bet.** That button will not appear in any
agent's catalogue, and a permanent check goes red if it ever does.

**If it goes wrong:** either agents get write access with no input validation (garbage lands in the
ledger), or the observe button leaks into an agent catalogue (a fabricated win becomes recordable),
or both gates pass only in prose (WO-103's G4 failure shape).

## The `qf_observe_ticket` ruling (architect, final — do not relitigate mid-build)

**Ruled: `observe_ticket` is served to no agent seat in this order, and its exclusion is a schema
property, not a name check.**

For the founder, in plain language: the system has two doors for bet slips. One is for AI proposals
and physically cannot accept a result. The other — "I placed this and here is how it settled" — is
yours. This order gives AI seats a catalogue of action buttons, and **your door is not in the
catalogue**. Not hidden, not permission-gated: never generated into any agent-facing surface at
all. The alarm that already watches this door (`observe-door`, plus the served-set check) stays on.
The door still has no lock — the lock is caller identity, ROADMAP debt #22, and it is not this
rung's job — but a door that appears on no agent's map and alarms when mapped is the strongest
position available short of that lock, and every stronger-sounding alternative we tried (six of
them) was defeated by a reader who did not write it.

**Mechanism (one meaning):** a new `operatorOnly: true` flag on the action definition
(`defineAction`), following the `pipelineFed` precedent (`define.ts:12,160,172`). The action tool
generator and the action server registration **skip any action carrying the flag**. The exclusion
is data the generator consumes — never an `if (name === "observe_ticket")`, which is route-naming,
which has now failed six times.

**The flag is machine-coupled to observation semantics, both directions**, so it cannot silently
rot. Precise rule (rewritten at the pre-build read — the first draft was creation-only and
ambiguous for multi-event actions like `resolve_hypothesis`, which has three command rows):

> Over **all** commands, creation and transition alike: an action is *observation-coupled* iff at
> least one of its commands' events ends `.observed`. `lintCommands` fails the schema unless
> `operatorOnly === observation-coupled` for every action — and additionally, a flagged action's
> **every** command event must end `.observed` (no action may be half-observation).

Today exactly one action is observation-coupled: `observe_ticket` (creation event
`ticket.observed`). A future `observe_run` inherits the exclusion by writing an observation event,
with no list to remember. **The lint must be generic over the rule, not over the known row** — G4
bait (c) exists specifically to kill the name-check-in-disguise implementation.

- **Schemas come from the schema package** — resolve action → Zod object from
  `qf-kernel-schema`; no schema duplicated into the Kernel (that is `ARTIFACT_KINDS`, debt #7,

## FOUNDER DECISION — served action tools advertise no parameters

Measured against the live registration: `qf_create_ticket`'s **transport `inputSchema` has zero
properties**. The real eight-field shape lives only in `_meta["qf/inputSchema"]`. A standard MCP
client listing tools sees a write tool with no discoverable arguments.

This is not builder error. In `@modelcontextprotocol/sdk@1.29.0`, `registerTool`'s `inputSchema`
takes a standard-schema (Zod) and **derives** the advertised JSON Schema from the same object it
validates with. Advertising the real shape therefore *makes MCP a second validator* — which D3
explicitly forbids, and which would mask GATE 1. Permissive-and-undiscoverable vs.
discoverable-and-double-validated is a genuine fork in this SDK, and the builder took the branch
the order mandated.

**It matters because WO-106's entire premise is "the cold seat proves discovery — no priming,
generated tools only."** As built, a cold seat cannot discover parameters. Escaping the fork means
serving `tools/list` from a low-level handler that emits the real JSON Schema while `registerTool`
keeps the permissive validator — real work, and a change to the agent-facing contract.

**Not delegated.** Logged as ROADMAP debt, trigger-gated to WO-106, for the founder to rule on with
the order in front of them. No builder should redesign the agent-facing surface unsupervised.
