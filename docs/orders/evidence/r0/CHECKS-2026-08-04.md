# R0 — the two remaining acceptance checks

Captured 2026-08-04 against the installed application at
`C:\Users\rybow\QuantFlow-L1-Acceptance\install`, driven over the app's own JSON-RPC socket rather
than by clicking. Both were previously recorded as untested.

**In plain terms.** The app now provably survives Hermes being missing, and stopping an agent
mid-thought leaves nothing running behind it.

## Check 1 — the app opens when Hermes is absent

**Method.** Closed the app. Renamed `~/.local/bin/hermes` to `hermes.qfhidden` inside WSL and
confirmed `command -v hermes` found nothing. Launched the installed app. Probed `app.readiness`, then
attempted a real `qf.dock.spawn`. Restored the binary in a `finally` block and re-confirmed it on
`PATH`.

| Criterion | Result |
|---|---|
| App opened without Hermes (`canvas: true`) | **PASS** |
| Dock still visible — 3 profiles listed | **PASS** |
| Spawn refused instead of hanging or silently succeeding | **PASS** |
| Refusal explains what to do | **PASS** |
| App still served RPC after the failed spawn | **PASS** |

The refusal, verbatim:

> `Hermes unavailable: "hermes" is not installed in the selected WSL2 distro. Install Hermes in Ubuntu/WSL2, then retry.`

Readiness reported `dockProfileIds: ["hermes-orchestrator", "hermes-worker", "hermes-worker-2"]` —
the Dock lists profiles from Kernel rows regardless of whether the runtime is installed, and
availability is resolved at launch. That is the correct split: the catalog is Kernel truth, and
availability is a runtime fact discovered when you try to use it.

## Check 2 — cancelling a seat mid-work

**Method.** Spawned `hermes-worker` from the Dock over RPC, wrote a long task into its terminal, and
confirmed the seat was actively producing output. Then removed its tile while it was still working.

```
BEFORE CANCEL   kernel=running   tile present
+3s             kernel=closed
+5s             kernel=closed
+7s             kernel=closed
tile still on canvas: false
```

| Criterion | Result |
|---|---|
| Seat was genuinely mid-work when cancelled | **PASS** — terminal was streaming output |
| Cancel took effect promptly | **PASS** — under 3 seconds |
| Tile removed from the canvas | **PASS** |
| Kernel status honest (`closed`, not stuck `running`) | **PASS** |
| No orphaned Hermes processes in WSL | **PASS** — `ps` shows none |

**A measurement error worth recording.** The first pass counted orphans with
`pgrep -c -f hermes`, which matches the `bash -c` command line running the check itself, so it
reported a floor of 1 and looked like a persistent orphan. Re-measured with
`ps -eo pid,etime,cmd | grep -i hermes | grep -v grep`, which returns nothing: the true count is
**zero**. Same class of error as counting CR bytes in binary files — a pattern that matches its own
observer. The corrected result is stronger than the flawed one, which is exactly why it was worth
re-measuring rather than reporting the floor as a caveat.

## What these do not prove

- Neither check involved the founder's eyes. They assert mechanical behaviour — the app comes up, the
  refusal is actionable, the process set returns to baseline. They do not assert the founder finds
  the Dock's unavailable state *clear*, only that it exists and says what to do.
- Check 1 hid the binary from `PATH`. It did not simulate a broken WSL distro, a missing Ubuntu, or a
  Hermes present but unauthenticated. Those remain untested.
- Check 2 cancelled by removing the tile. Cancelling from inside the seat's own TUI (Ctrl-C at the
  Hermes prompt) is a different path and was not exercised.
