# ADR-0004 — Repository Golden Baseline before R18

status: **ACCEPTED**
date: 2026-08-24
decision-maker: founder
applies-before: R18 Ground & First Use

## Context

The read-only Repository Intent Audit at
`5882ab2febf00f2c15a94c868c191420ed561bb4` accounted for all 1,150 tracked
files, all 153 direct dependency declarations, all 19 Electron package
declarations/hooks, and 40 bounded operational roots. Its independent derived-
packet review failed once, the five publication defects were corrected, and the
independent recheck passed at receipt SHA-256
`000BA6BE7DE6227FF850F61EE2DB35E3F72AB49DECAC670893F774ECB3E8CC38`.

The audit found a real retained product core plus obsolete runtime islands,
stale active-context history, unsupported package claims, duplicate semantic
authority, and current product/test defects. R18 would make those seams more
expensive to repair.

## Decision

### 1. Golden program

R18 remains selected but frozen. Before R18, QuantFlow executes:

```text
Phase 2 — twelve individually gated surgical purification groups
→ Phase 3 — one complete clean-source Windows product requalification
→ one immutable Golden SHA
→ R18 Ground & First Use
```

Phase 2 preserves the accepted R0–R17 and Pre-R18 product floor. It is not a
rewrite, a new product rung, or permission to add future-rung capability. Only
one group receives build authority at a time through `NEXT.md`.

### 2. Approved Phase-2 groups

The founder approves the audit's G1–G12 structure, each with its own literal
scope, pre-proof, rollback boundary, focused Builder proof, and independent
Verifier. A group may not widen itself merely because nearby debt exists.

1. exact generated and local authority residue;
2. unbuilt and superseded residue;
3. peer-bus and critic-mock islands;
4. AgentOS runtime fossil while preserving independently required `.aospkg`
   identity;
5. legacy ACP, Agent Chat, and standalone Terminal islands;
6. false Claude production identity;
7. unconsumed protocol and direct-dependency contraction;
8. Kernel, schema, law, and proof-integrity repair;
9. one current Report/result authority;
10. ordinary Canvas, Mission/full-lineage lens, and runtime-truth coherence;
11. current authority and active-context history compression;
12. Windows package and operations hardening.

### 3. Two explicit defect owners

The `qf-bovada-football` Windows `fsync EPERM` failures belong to **G12**.
G12 must make the real domain assertions execute and pass on supported Windows
filesystem behavior; a wrapper-only or pre-assertion green is not acceptance.

The process-local `researchEvidenceByRunId` map in
`collab-electron/src/main/kernel.ts` belongs to **G9** as a current Golden
defect. Report publication may not depend on volatile process memory. G9 must
derive the exact Run-to-worker-evidence binding from Kernel-owned durable truth,
prove mid-journey close/reopen, and remove the map without adding a second
store.

### 4. Law B

G8 determines the intended write invariant before changing it. It may not
weaken Law B merely to declare the current governed-review implementation
compliant. Law, implementation, gate, falsifier, and receipt must end with one
meaning.

### 5. Schema lifecycle

All 89 current lifecycle declarations remain intentionally `experimental` for
the founder-alpha Golden Baseline. Golden certifies implementation health, not
public schema stability. Only the founder promotes a type under ADR-0002.

The stability trigger is the earlier of the first external state-compatibility
promise or R25 Deliver & Operate acceptance.

### 6. Supported platform

Windows x64 is the sole current Golden product platform. WSL may remain a
Windows implementation dependency; that does not make Linux a supported
QuantFlow product platform. macOS/Linux product/package claims leave or are
disabled unless a later explicit decision funds their equivalent full
qualification.

### 7. Developer instruments

- **Atlas:** keep as an exact-SHA static architecture instrument. It never
  becomes Kernel or product truth.
- **qf-vault-projection:** retain only as a read-only, explicitly invoked
  founder developer instrument if G11 proves current invocation and authority
  boundaries. Otherwise retire it in G11. It never writes product truth.
- **Canvas skill/CLI:** target retirement from active main in G11 unless a
  current deliberate founder or agent workflow is proved. Historical novelty
  is not retention evidence.
- **GLACIER:** archive outside active main after hash preservation. It is not
  the selected implementation target.
- **`.mcp.json`:** remove in G11 unless an exact current developer workflow is
  named and bounded.

### 8. Golden closure

Phase 3 starts from the frozen, independently accepted Phase-2 candidate and
requalifies the complete remaining supported repository and product. It must
meet the read-only audit's requalification contract and binding amendments,
including new full file/dependency/resource accounting, zero known current
defects or unexplained reds, clean Windows build/package, naive and founder
product traversal, read-only Kernel agreement, close/reopen, and process zero.

### 9. Execution throughput without proof dilution

For G2 through G12 and Phase 3, the program uses these standing execution rules:

1. Freeze each future group's exact focused acceptance matrix against its
   starting SHA before its Builder opens. Separate pre-existing reds from
   candidate-introduced reds before mutation.
2. While an immutable candidate is under independent verification, the next
   group's fresh Reader may perform provisional read-only source scoping.
   Neither next-group authority nor a mutating Builder opens before the current
   group independently passes.
3. Mutually independent verification commands may run concurrently only when
   they cannot mutate shared state.
4. Exact-SHA receipts may be reused when the relevant bytes and configuration
   are unchanged. Proof is not rerun solely for ceremony.
5. Clean install, full generation, full package and full current-product
   traversal are reserved for groups that materially touch those boundaries and
   for mandatory Phase 3.
6. Mechanical same-meaning proof-harness corrections use the shortest
   trustworthy independent verification path. A fresh Reader is required only
   when a red could change product behavior, semantic authority, acceptance
   meaning, group scope/order, supported compatibility, or what a PASS means.
   A red proven at the frozen starting SHA and limited to path classification,
   a stale selector, an allowlist entry, harness invocation, teardown,
   generated proof metadata, or receipt formatting may be repaired directly
   by the Router under the Reader-approved order. That correction must retain
   the assertion and prove the old red, new green, and focused non-regression.
7. A documentation/evidence-only commit after an immutable product candidate
   does not force the complete matrix to rerun. Product-tree and relevant
   configuration identity must be proved by hash, after which exact-byte
   receipts remain reusable.
8. Known harness preconditions, especially Atlas clean-tree requirements, are
   computed before Builder mutation so evidence/commit ordering does not create
   procedural stops.
9. Every final group candidate still requires one independent Verifier. The
   Verifier falsifies the candidate; it does not become a second Builder or
   reopen already-proved semantics.
10. A proven pre-existing red outside a group's semantic ownership is recorded
   against its already named Golden group instead of being absorbed, provided
   the active group's non-regression can still be independently proved.

These rules do not combine groups, parallelize mutating Builders, weaken
acceptance, skip immutable candidates or independent verification, or alter the
Phase-3 closure standard.

## Consequences

- `NEXT.md` temporarily authorizes Phase-2 groups while keeping R18 frozen.
- No obsolete system is removed merely because it is old; every deletion earns
  consumer, package, compatibility, QA, and future-route proof.
- Reachability does not justify retention.
- Future usefulness does not justify current complexity when recreation is
  cheaper.
- Phase 2 can finish with fewer files or similar line count; success is one
  intentional authority per semantic job and no known stale production burden.

## Rejected alternatives

**Proceed directly to R18.** Rejected because it would build acquisition on top
of known Report, Mission, runtime-state, packaging, and repository-purpose
defects.

**Delete all legacy-looking code at once.** Rejected because package identity,
state compatibility, and current QA can depend on a small part of an otherwise
obsolete subsystem.

**Rewrite QuantFlow.** Rejected because the audit proved the Kernel/Ontology,
Electron shell, Canvas, Dock, Hermes path, and research lineage are real retained
architecture.
