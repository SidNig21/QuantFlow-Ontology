## In plain terms

Right now the schema is one big file, and a lot of the descriptions in it read like labels on a
filing cabinet. This order splits it into three files by subject and rewrites those descriptions
so an AI agent reading them cold knows not just *what* a thing is but *what rule governs it*.
Nothing about how the software behaves changes.

**If it goes wrong:** agents keep guessing at what your data means, and every later step — the
tools, the research loop, the whole point of this — inherits the guessing. Nothing breaks
loudly. It just quietly stays vague forever.

## Gates

**G1 · Lint falsification (builder-run).** Three sabotages each go red, then restore to green:
a missing description · a `backtest_run` clone · a property removed from an `active` fixture
type. Bait transcripts in the report, both directions.

**G2 · The cold-read protocol (verifier-run, not CI).** Ship `qa/fixtures/charter-101.md`
containing the protocol below. A cold agent is given **only the three plane files** — no
database, no other docs — and asked:

> *"Using only these type definitions: I want to know which runs testing a given hypothesis
> produced a supporting evaluation, and which published artifact those evaluations gated. Name
> the exact types, the exact links, and the exact field and value that means 'supporting'. If
> anything needed is missing from these files, say what."*

This tests **descriptions, not data** — which is why it needs no rows and works today.

Pass = the agent names `hypothesis`, `run`, `evaluation`, `artifact`; names `tests`, `produces`,
and `evaluated_by`; and identifies **`evaluation.verdict === "supports"`** as the predicate.
`confidence` is a separate 0–1 field and is **not** the gate — an agent that conflates them found
a description defect.

> **Criteria correction, 2026-07-25 (architect, after the build, before verification).** This
> line originally also required `derived_from`. That requirement was **wrong**. The question asks
> which published artifact the evaluations *gated* — reachable through `evaluated_by` alone.
> `derived_from` only enters if you assume the gated thing is a report *derived from* the
> evaluated result set: an assumption baked into the criteria and never stated in the question.
> A reader who omits `derived_from` and explains why is answering the question as asked.
>
> This is a defect in **the order**, not in the build and not in the descriptions. Corrected here
> rather than left standing, because grading a build against a bar its author already knows is
> wrong is worse than either passing or failing it honestly. **The verifier still owns the
> pass/fail call — including whether this correction is itself right.**

A wrong answer is a **description defect** — fix the description, not the protocol.
**Escape hatch:** if the correct answer is genuinely unexpressible because the schema lacks the
field or link, that is a **schema finding to log in your report**, not a description to reword.

**Second question, asked separately and scored separately — also required:**

> *"Using only these files: can you express which evaluation authorized a specific published
> report? If not, name exactly what is missing."*

Pass = the agent answers **no**, and identifies that `evaluation` has no outbound link — the
only edge touching it (`evaluated_by`) points *at* it — so nothing marks which publication a
verdict authorized. `derived_from` is not a valid substitute; two reports may derive from one
result set and one evaluation with nothing distinguishing them.

This is asked as its own question on purpose. Folding it into the first would make a builder
with flawless descriptions fail because their reader lacked one insight — a gate going red for
the wrong reason. Asked directly, it is falsifiable and it tests the descriptions, not the
reader's brilliance.

### Found during this order (2026-07-25) — added per the line above

Findings 5–10 came out of the **G2 cold reads**, which is worth noting on its own: the gate meant
to test description quality also functioned as a schema audit, because an agent that can read the
charter properly can also see what the charter cannot say. Full transcripts in

5. **`record_evaluation` carries no subject reference.** Its input is
   `{metrics, verdict, confidence, rationale, critic_findings_ref}` — no `hypothesis_id`,
   `run_id`, or `artifact_id`. So even after finding #3 is fixed and the command is wired, the
   action still cannot create the edges WO-111's closing proof must traverse. This *compounds*
   #3; wiring the command alone does not resolve it.
6. **The approval actions reference object types that do not exist.** `request_approval` takes
   `subject_ref: string`, `approve`/`deny` take `request_id: string`, and there is no
   `approval_request` or `approval` object anywhere in the schema. Operator authorization exists
   only as action arguments pointing at ids that nothing backs.
7. **Nothing on the proof path carries a timestamp.** Neither `evaluation`, `artifact`, nor `run`
   has a created-at or decided-at field. `dataset.as_of`, `event.starts_at` and
   `result.settled_at` show the schema times things deliberately elsewhere — but on this path,
   precedence is unprovable from data. "The evaluation preceded the publication" is the minimum
   evidence for the word *gated*, and WO-110's gate will need it.
8. **`artifact` has no published state.** No status field, so a published report is
   indistinguishable from a merely registered one; publication is inferred from a row existing.
9. **Two near-identical states with nothing keeping them consistent.** `hypothesis.status ===
   "supported"` and `evaluation.verdict === "supports"` differ by one character, live on
   different objects, and no link or rule relates them. The cold reader flagged this unprompted
   as a confusion risk for exactly the agents this charter serves.
10. **Evidence pointers are strings, not links.** `critic_findings_ref`, `spec_ref`,
    `contract_ref`, `system_prompt_ref` are plain strings, so the evidence behind a verdict is
    not traversable.
